# Gemma 4 実推論による修正・評価（2026-09-12）

## 対象と方法

Gemma 4 E4B INT4 / E2B INT4 のインストール済み ONNX 重みを使用。教材バンクの数学・英語と合成クラス集計を、実装と同じプロンプト・推論・検証・ヒントガードへ通した。モックは不許可。個人の授業データや解答は使用していない。

`src-tauri/src/ai/evaluation.rs` の opt-in テストは生成と診断記録のためのもの。テスト成功だけで意味的正確性を保証せず、下記 JSON の生出力と実際の返却値を人手で照合した。記録にはプロンプト、モデル名、生成時間、途中終了、JSON 検証、ガード適用、分類一致を含む。

## 実推論で見つかった問題と修正

1. E4B の CoreML 実行は2回目の要求で SIGSEGV。macOS 診断のスタックは BNNS / Espresso batch matmul / CoreML prediction を指した。Rust の Result では回復できないため、Gemma 4 の decoder/embed はこの構成で CPU 実行に切り替えた。他のモデルのプロバイダ選択は従来通り。
2. CPU に変えるだけでは「問題問題」「y = =」や誤った数式が残った。同一教材・プロンプトでダミー KV キャッシュ1位置を取り除くと重複がなくなり、正しい問題引用・割合・分類が得られた。Gemma 4 は空キャッシュで開始し、注意マスクも実際のパディング長に合わせる。比較記録: [CPU+旧キャッシュ](gemma4/e4b-baseline-cpu.json)、[空キャッシュ](gemma4/e4b-empty-cache.json)。一般のモデルへの普遍的な結論ではなく、このエクスポートの観測結果。
3. EOS 前のトークン上限到達を `truncated` として扱う。空出力・デコード失敗を偽の実モデル回答へ置き換えない。授業案の不正 JSON は1回だけ修復生成し、なお不正なら教材・集計による案へ戻す。
4. 教材で定義された既知誤答は正規化後の対応を優先し、モデルによる上書きを禁止（本番では推論も省略）。未知誤答の分類は既知コード・既知ラベル・完全一致する `code=label` のみ許可。不一致ペアや説明文中のコードは拒否。採点はモデル任せにせず、正規化した正答集合による判定を維持。
5. ヒントは今回の解答と「実際に表示した」直近3ヒントを渡す。教材ヒントの情報量を保つ短い言い換えに絞り、正答の数値・英語活用形・LaTeX を追加しないよう指示。正答漏洩や表示済みヒントの再出力（空白・句読点の違いを除く）は教材ヒントへ戻し、長文は途中で切らず完成した教材ヒントへ戻す。
6. 授業案は4段階・短い活動・具体的な確認問題に限定。回答0件は未収集の注記をアプリ側でも確定する。誤概念なしを「回答なし」と混同しない。
7. E2B は未収集の内部既定値0をそのまま正答率として復唱した。教師用プロンプトでは未収集の指標を null とし、説明も「不明」に変更。誤概念の件数・割合は日本語の読み取り文にも含めた。

Gemma 4 のテキスト会話形式は [Google の公式 chat template](https://huggingface.co/google/gemma-4-E4B-it/raw/main/chat_template.jinja) と照合した。今回の原因として会話区切りを変更する必要はなかった。現在の生成は greedy decoding であり、temperature 指定で多様性を制御できる実装ではない。

## 評価結果

E4B の最終ヒント・授業案: [生成記録](gemma4/e4b-final-prompts.json)。3種類の授業案（誤概念あり・未収集・誤概念なし）は各1回目でスキーマ適合。数学3段階と英語のヒント4件はガードによる差し替えなしで正答漏洩を避けた。以前のプロンプトでは英語の `went`、数学の正答3が出る例を実際に検出し、教材へ戻ることも確認した（[改訂途中](gemma4/e4b-revised.json)）。

代表例:

- 数学分類: `m0=傾きと切片の混同` → 既知ラベルに解決。
- ヒント1: 「xが1増えたとき、yがいくつ増えるかに注目して考えよう。」
- ヒント2: 「変化の割合は、y=ax+bのaに相当します。」
- 英語: 「yesterdayは過去を表すので、goを過去形にしましょう。」

E4B CPU の記録ではヒント約9〜11秒、授業案約65〜70秒。これはデバッグビルドでの少数の診断計測であり、ベンチマークではない。CoreML の旧速度表と品質を同一視しない。モデルを変更しても教師による確認・編集は必要であり、この少数例は全教材での品質保証ではない。

## 再現

ユーザーの永続的なモデル選択を変えず、一時ディレクトリにモデルへのリンクと `active_model.json` を置いて実行した。

```sh
LUMIN_AI_SMOKE_MODEL_DIR=/tmp/lumin-gemma4-eval/models \
LUMIN_AI_EVAL_OUTPUT=/tmp/lumin-gemma4-eval/result.json \
cargo test --manifest-path src-tauri/Cargo.toml --lib classroom_model_evaluation -- --ignored --nocapture
```

`LUMIN_AI_EVAL_CASES=teacher_facts,teacher_empty` のように対象を限定できる。E2B は対応する一時モデルルートと variant `4-e2b-int4` を使う。複数モデルの推論は同時に走らせない。

## E2B と実画面での追加確認

- [E2B の11条件](gemma4/e2b-final.json): 授業案3条件は初回生成でスキーマ適合。教師チャットの未収集復唱、英語の誤分類、数学ヒントの繰り返しを検出した。
- [教師プロンプト改訂後](gemma4/e2b-teacher-revised.json): 問題文・正答率60%・主な誤概念を正しく回答。未収集は「正答率・再挑戦成功率・誤概念は不明」と回答。
- [分類・ヒント対策後](gemma4/e2b-guards-revised.json): 数学分類は生出力も一致。英語は対応表を渡してもモデルの生分類は不一致だったが、返却値は教材で定義された「時制の読み落とし」を保持。ヒント3の繰り返しを検出し、x の直前の数を見る教材の手順へ差し替えた。E2B のヒント1/2はまだ抽象的で、E4B と同等の具体性とは評価しない。
- 最新の教師プロンプトを使用するネイティブ .app でも E4B 実推論を実行。合成データの「48%、傾きと切片の混同7件」と画面上の回答が一致。1024×720 の実画面で回答・入力欄を確認し、ページ全体の飛びや画面外への入力欄の押し出しはなかった。
- 最初のネイティブ検証では外付けボリュームへのモデルリンク経由で tokenizer の `open` が待ち続けた（スレッドサンプルで確認）。一時ローカルコピーで回答完了した。OS 側の待ちの根本原因は未確定であり、推論アルゴリズムの修正で解決したとは扱わない。アプリの通常モデル配置先は Application Support。検証用 .app のリンクは撤去し、永続的なモデル選択は変更していない。
