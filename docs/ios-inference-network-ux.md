# iPhoneの推論・教室通信・操作パネル

2026-09-13。前回の[UI検証](ios-ui-audit.md)で未解決だった手動参加と実モデル推論を対象にした追加修正。

## iPhoneの操作

Apple HIGの[Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)、[Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)、[Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets)、[Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)を確認した。

HIGは、ツールバーに操作を詰め込みすぎず、補助的な操作をまとめること、画面の狭さに応じてサイドバーよりコンパクトな操作を選ぶことを勧めている。これに合わせ、スマホではモデル情報等を常時表示する紫色の帯をなくし、右上の「…」から開くダイアログへまとめた。頻繁に使う先生の画面切り替えは直接選べる。上部の操作領域は約120pxから48pxになった。

入力中の補助表示はフォーカス移動ではなくキーボードの表示領域に連動させ、タッチ中は入力欄のフォーカスを維持し、タッチ終了とクリックの重複から二重送信されることも防いだ。チャット履歴は表示領域の変更後も末尾へ追従する。先生画面を開いただけではAIモデルをロードせず、チャットを初めて開く時に読み込む。

操作パネルは標準HTML dialogのモーダル動作を使い、フォーカスの範囲を制限し、閉じる操作で元の画面へ戻る。44px以上のタップ領域、safe area、横向き、入力中の表示領域を考慮した。TauriのWebView内の実装であり、SwiftUI/UIKitのネイティブコントロールへの置き換えではない。

## 教室通信

- 手動入力では教室UUIDが空だったため、サーバーのUUID認証で403になっていた。参加コードで `/session/resolve` から現行UUIDを解決し、その後の参加・結果送信には参加コードとUUIDの両方を付ける。
- 参加応答に配信中の問題とUUIDを含める。生徒端末のローカル問題で応答を上書きする処理を削除した。
- 生徒が参加した接続先と参加者トークンを保持し、匿名の `AnalysisEvent` を先生端末へHTTP送信する。以前は生徒側のメモリに保存するだけだった。
- サーバーの受信イベントを先生の集計と共有し、受信通知で画面を更新する。未登録の参加者や別セッションの結果は拒否する。
- 結果送信に失敗した場合は問題画面に残り、再送できる。再送時のイベントIDを保持し、サーバーは同じIDを重複集計しない。送信が成功した後だけ完了表示へ進む。

HTTP送信の型は正誤・誤概念・ヒント回数・再回答結果等に限定され、解答本文は含めない。既存のローカルHTTP通信であり、インターネット越しの利用を追加する変更ではない。

## 実モデル推論

対象はGemma 3 1B INT4と、ユーザーが指定したGemma 4 E2B INT4。既存のローカルONNXファイルをシミュレータのアプリコンテナに配置し、ネイティブの教師チャットから実行した。さらにGemma 4 E2B INT4は物理iPhoneへ導入し、教師チャット、誤答ヒント、レッスンプランから実行した。

Gemma 4はCoreML非対応の明示的なガードで停止していた。iOSではWebGPUの動的プラグインを使えないため、Gemma 4には同じ静的ONNX RuntimeのCPU実行をモデル別の標準設定として選ぶ。Gemma 3はCoreMLを維持する。モデル一覧でiPhone上のCPU実行と待ち時間を説明する。明示的な実行プロバイダの環境変数は優先し、エラー発生後の自動フォールバックは加えていない。

Gemma 3は「1 + 1 = 2」、Gemma 4 E2Bは「1+1は2です。」という実際の回答をシミュレータで確認した。教師チャットはモック推論を回答として採用しないため、モデル未導入時の定型表示ではない。E2Bでは誤答からヒント表示、5問完了も確認した。さらに同じ会話で「その答えに3を足すと」と追質問し、「5」と回答することを確認した。Gemma 3でも追質問に「2 + 3 = 5」と答え、末尾が表示されることを再確認した。

物理iPhoneの教師チャットでは「1+1は2です。」、同じ会話の追質問では「5」を確認した。誤答ヒントは約9秒で生成され、レッスンプランは約102〜103秒で検証を通った編集可能な案になった。E4BとGemma 3nは今回の物理端末検証の対象外で、長時間利用時の発熱・電池消費も未計測。

## 検証と証拠

Rustの通常テスト218件（実モデル等の手動実行テスト19件はignore）、フロントエンド88件、静的チェック、Webビルドを実行した。ネイティブは `aarch64-sim` を明示してビルド・インストールした。

実アプリのXCTestは前回のHTTPフィクスチャを使わず、実際の教室サーバーに対して参加、5問完了、先生集計への反映を検証した。まずiPhone 17eを先生、iPhone 17 Proを生徒として別々のシミュレータで起動し、手動参加から5問完了まで操作した。

その後、Macのネイティブ先生アプリを `192.168.10.25:8765` で起動し、USB接続した物理iPhone 17のUI Test RunnerからWi-Fi経由で参加した。参加コード解決、問題取得、5問の結果送信が成功し、Mac側に参加者1人・全5回答・初回正解率100%・匿名シグナル5件が表示された。これは物理iPhoneとMacの実LAN通信を確認するもので、Bonjour自動発見自体は手動接続とは別経路のため保証しない。

レッスンプランの実装確認では、構造化出力が検証を通らず教材ベースへフォールバックした場合、その進捗表示が生成完了と同時に消えてAI生成成功のように見える問題を確認した。完了後も「教材に基づく案」であることと確認を促す表示を残すよう修正した。実機で行った2回の生成は最終的に検証を通り、この通知自体の分岐は再現可能なフロントエンドテストで確認した。

ローカルのログ・XCTestコード・スクリーンショットは `.build/ios-ui-audit/` に保存する（git管理外）。Xcode 27のアプリ画像には横向きの取得異常があるため、横向きの視覚確認にはsimctlの画像を使う。

キーボード中の送信検証では、XCTestの通常の `tap()` がWebViewの自動スクロールを挟むケースを確認したため、最終検証は送信ボタンの表示位置の中心を座標タップした。E2Bの追質問への回答が生成され、回答要素が画面内で操作可能であることも検査した。画面画像は `followup/e2b-followup-final.png`、横向きは `followup/landscape-final.png` に保存した。

## アイコンと導線の追加見直し

PC・スマホとも「AI 先生方へ質問」の説明枠を削除した。上部の「操作」を三点アイコンへ、設定と操作パネルの「閉じる」を×へ変更し、読み上げ用の名前と44pxの操作領域は維持する。左上はグリッドアイコン＋「役割」で役割選択へ直接戻る。先生内の画面履歴へ戻る矢印と混同しないため、単独の「＜」は使わない。

PC・横向きの広い画面では既存のサイドバー、縦向きの狭い画面では先生内の4画面を直接選べるナビゲーションを維持した。頻繁な画面切り替えを毎回メニュー内へ隠すより、役割選択と設定の導線を分離して操作回数を減らす構成を選んだ。

スマホの作業領域の下側の余白を10pxから0へ減らした。ホームインジケータのsafe areaは残している。角丸は外側28pxと内側12〜16pxを余白に合わせて調整した。Appleの[同心的な形状のガイド](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)に合わせたWebView上の調整であり、SwiftUIのConcentricRectangleや端末の物理ディスプレイRを自動取得する実装ではない。

追加後、iPhone 17eの先生各画面・設定のスクロール・×での復帰・質問の下書き保持・左上からの役割変更・生徒参加画面・デモ完了・Gemma 4 E2Bの実推論と追質問をXCTestで確認した。PC幅ではSafariでチャット・三点メニュー・モデル状態を実表示した（Safariでの推論は検証対象外）。

最終のアイコン版の画像は `followup/graphic-ux/34-followup-result.png`、`followup/graphic-final/60-graphic-chat.png`、`followup/graphic-landscape.png`。メニューを開く時は内容のマウント後にモーダル化し、×ボタンへフォーカスが移るようにした。
